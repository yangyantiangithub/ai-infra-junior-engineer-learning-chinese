## 系统概述

本项目实现了一个简单的 REST API，用于提供来自预训练图像分类模型的预测。系统采用无状态、容器化的微服务架构模式，这是生产级 ML 系统中常用的模式。

### 关键特性

- **无状态：** 无服务端会话状态，支持水平扩展
- **容器化：** 使用 Docker 打包，实现跨环境一致部署
- **同步：** 请求-响应模式，阻塞式推理
- **单模型：** 每次只服务一个模型版本（尚无 A/B 测试）
- **CPU 优化：** 专为 CPU 推理设计（后续项目支持 GPU）

### 设计理念

本架构优先考虑：
1. **简洁性：** 易于初学者理解和调试
2. **可靠性：** 优雅的错误处理和恢复
3. **可观测性：** 全面的日志记录便于故障排除
4. **可维护性：** 清晰的关注点分离，模块化设计

## 组件设计

### 1. API 层 (app.py)

**职责：** HTTP 请求/响应处理、路由、API 契约执行

**关键组件：**
- Flask/FastAPI 应用实例
- 每个端点的路由处理器
- 请求验证中间件
- 响应格式化工具
- 错误处理中间件

**设计模式：** MVC（模型-视图-控制器）- API 层充当控制器

**接口：**
```python
class ModelAPI:
    """主 API 应用类"""

    def __init__(self, model_loader: ModelLoader, config: Config):
        """使用依赖项初始化 API"""

    def predict(self, request) -> Response:
        """处理 /predict 端点"""

    def health(self) -> Response:
        """处理 /health 端点"""

    def info(self) -> Response:
        """处理 /info 端点"""
```

### 2. 模型管理器 (model_loader.py)

**职责：** ML 模型生命周期管理、推理执行

**关键组件：**
- 从预训练权重加载模型
- 图像预处理流水线
- 推理执行
- 结果后处理
- 类别标签映射

**设计模式：** 单例模式 - 每个应用一个模型实例

**接口：**
```python
class ModelLoader:
    """管理 ML 模型生命周期"""

    def __init__(self, model_name: str, device: str = "cpu"):
        """使用模型配置初始化"""

    def load_model(self) -> None:
        """加载模型权重并初始化"""

    def preprocess(self, image: PIL.Image) -> torch.Tensor:
        """预处理图片以供推理"""

    def predict(self, image: PIL.Image, top_k: int = 5) -> List[Prediction]:
        """为图片生成预测"""

    def get_model_info(self) -> ModelInfo:
        """返回模型元数据"""
```

### 3. 配置管理器 (config.py)

**职责：** 应用配置管理、环境变量处理

**关键组件：**
- 环境变量加载
- 配置验证
- 默认值管理
- 类型转换

**设计模式：** 配置对象

**接口：**
```python
class Config:
    """应用配置"""

    # 模型设置
    MODEL_NAME: str
    MODEL_PATH: str
    DEVICE: str  # "cpu" 或 "cuda"

    # API 设置
    HOST: str
    PORT: int
    DEBUG: bool

    # 限制
    MAX_FILE_SIZE: int
    REQUEST_TIMEOUT: int

    # 日志
    LOG_LEVEL: str
    LOG_FORMAT: str
```

### 4. 日志系统

**职责：** 结构化日志、请求跟踪、错误报告

**关键组件：**
- 日志记录器配置
- 关联 ID 生成
- 结构化日志格式化（JSON）
- 日志级别管理

**设计模式：** 装饰器模式用于请求日志记录

## 技术栈

### 编程语言
- **Python 3.11+**
  - 理由：优秀的 ML 生态系统、可读性、生产力
  - 考虑的替代方案：Go（缺乏 ML 库）、Java（冗长）

### Web 框架
- **Flask 3.0+** 或 **FastAPI 0.100+**
  - Flask：更简单、更传统、文档丰富
  - FastAPI：现代化、支持异步、自动 API 文档、类型验证
  - 给初学者的建议：Flask（复杂性较低）

### ML 框架
- **PyTorch 2.0+** 或 **TensorFlow 2.13+**
  - PyTorch：更直观、调试更好、对研究友好
  - TensorFlow：生产就绪、生态系统更广、TF Serving 集成
  - 建议：PyTorch（学习曲线较平缓）

### 图像处理
- **Pillow (PIL Fork)**
  - Python 图像处理的行业标准
  - 替代方案：OpenCV（对本用例来说过于庞大）

### 配置
- **python-dotenv**
  - 从 .env 文件加载环境变量
  - 替代方案：手动 os.environ（不够方便）

### 测试
- **pytest**
  - 现代化、功能丰富的测试框架
  - 替代方案：unittest（更冗长）

### 容器化
- **Docker 24.0+**
  - 容器化的行业标准
  - 基础镜像：python:3.11-slim（更小、更快）

## 设计决策

### 1. 同步 vs 异步

**决策：** 同步（阻塞）请求处理

**理由：**
- 对初学者实现更简单
- ML 推理是 CPU 密集型（而非 I/O 密集型）
- 更少的并发问题
- 更易调试

**权衡：**
- 高并发下吞吐量较低
- 请求排队可能导致超时
- 对于长时间运行的请求不是最优

**未来考虑：** 在后续项目中迁移到异步（FastAPI）

### 2. 模型加载策略

**决策：** 启动时一次性加载模型，保持在内存中

**理由：**
- 更快的推理（没有每次请求的加载开销）
- 更简单的代码（不需要缓存逻辑）
- 可接受的内存占用（ResNet-50 小于 500MB）

**权衡：**
- 更高的内存使用
- 启动时间较慢（20-30 秒）
- 无法热切换模型

**考虑的替代方案：** 懒加载（首次请求时加载）- 因首次请求延迟过大而被拒绝

### 3. 单模型 vs 多模型

**决策：** 每个实例一个模型

**理由：**
- 更简单的部署和管理
- 可预测的资源使用
- 更易监控和调试

**权衡：**
- 无法进行 A/B 测试
- 模型更新需要重新部署

**未来路径：** 高级项目中的多模型服务

### 4. CPU vs GPU

**决策：** 本项目仅使用 CPU

**理由：**
- 更低的成本（无需 GPU 实例）
- 更简单的设置（无需 CUDA 配置）
- 足够的学习性能（延迟 < 1 秒）

**权衡：**
- 更高的延迟（300-500ms vs GPU 上的 50-100ms）
- 更低的吞吐量

**未来路径：** 后续项目中的 GPU 优化

### 5. 图片存储

**决策：** 仅内存（不持久化到磁盘）

**理由：**
- 更快的处理
- 无磁盘 I/O 开销
- 更简单的清理（自动垃圾回收）
- 降低安全风险

**权衡：**
- 无法重放请求
- 没有输入审计记录

### 6. 日志策略

**决策：** 结构化日志输出到 stdout/stderr

**理由：**
- 与容器编排兼容
- 易于与云日志集成（CloudWatch、Stackdriver）
- 无文件系统依赖

**格式：** 生产环境使用 JSON 结构化日志，开发环境使用文本

## 可扩展性考虑

### 水平扩展

应用设计为可水平扩展：

```
                  ┌──────────────┐
                  │   负载均衡器  │
                  └──────┬───────┘
                         │
           ┌─────────────┼─────────────┐
           │             │             │
           ▼             ▼             ▼
      ┌────────┐    ┌────────┐    ┌────────┐
      │ API    │    │ API    │    │ API    │
      │ 实例 1 │    │ 实例 2 │    │ 实例 3 │
      └────────┘    └────────┘    └────────┘
```

**扩展特性：**
- 无状态设计（实例之间无共享状态）
- 每个实例独立加载模型
- 无数据库依赖
- 无会话认证（如添加）

**限制：**
- 无共享缓存（每个实例独立加载模型）
- 启动时间线性增长（所有实例都要加载模型）
- 总内存 = 每实例内存 × 实例数

### 垂直扩展

对于单个实例的更高吞吐量：

**选项：**
1. **更多 CPU 核心：** 运行多个工作进程（Gunicorn/Uvicorn）
2. **更多内存：** 支持更大的批次或更大的模型
3. **添加 GPU：** 推理速度提升 10-20 倍

**建议：** 从 2 个 vCPU、4GB 内存开始（相当于 t3.medium）

### 性能优化路径

**阶段 1（当前）：**
- 单工作进程，CPU 推理
- 目标：10 请求/秒

**阶段 2（未来）：**
- 多工作进程部署（4-8 个工作进程）
- 目标：40-80 请求/秒

**阶段 3（未来）：**
- GPU 推理
- 目标：200-400 请求/秒

**阶段 4（未来）：**
- 模型优化（TensorRT、ONNX）
- 目标：500-1000 请求/秒

## 监控与可观测性

### 日志级别

```python
# INFO：正常操作
"Request received: correlation_id=abc123"
"Prediction completed: latency=234ms"

# WARNING：异常但可恢复
"File size near limit: 9.8MB"
"Request took longer than expected: 950ms"

# ERROR：请求失败
"Invalid image format: correlation_id=abc123"
"Out of memory during inference"

# CRITICAL：系统故障
"Model failed to load on startup"
"Health check failing"
```

### 要跟踪的指标

**请求指标：**
- 请求计数（按端点）
- 延迟（P50、P95、P99）
- 错误率（4xx、5xx）
- 请求大小分布

**资源指标：**
- CPU 使用率（%）
- 内存使用量（MB）
- 内存利用率（%）
- 磁盘 I/O（极少）

**应用指标：**
- 模型加载时间
- 推理时间
- 预处理时间
- 队列深度（如使用异步）
