## 系统概述

### 目的
将简单的模型服务 API 通过 Kubernetes 编排转变为生产级、高可用、自动伸缩的系统。该架构展示了大规模部署 ML 推理服务的行业标准实践。

### 关键特性
- **高可用：** 多副本自动故障转移
- **可伸缩：** 根据负载在 3 到 10 个 Pod 间自动伸缩
- **弹性：** 通过健康检查和自动重启实现自愈
- **可观测：** 全面的指标和监控
- **可维护：** 零停机部署和回滚

### 架构风格
- **微服务：** 单一用途的模型服务 API
- **容器编排：** Kubernetes 托管生命周期
- **云原生：** 基础设施即代码，声明式配置

## 组件详情

### 1. Deployment

**用途：** 管理 Pod 生命周期和滚动更新

**规格说明：**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: model-api
  namespace: ml-serving
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 更新期间可以创建 1 个额外的 Pod
      maxUnavailable: 0  # 始终保持最少副本数
```

**关键特性：**
- **声明式管理：** 指定期望状态，Kubernetes 维持该状态
- **自愈：** 自动替换失败的 Pod
- **滚动更新：** 逐步替换以实现零停机
- **回滚支持：** 维护修订历史

**Pod 模板：**
```yaml
template:
  spec:
    containers:
    - name: model-api
      image: model-api:v1.0
      ports:
      - containerPort: 5000
      resources:
        requests:
          cpu: 500m
          memory: 1Gi
        limits:
          cpu: 1000m
          memory: 2Gi
```

### 2. Service (ClusterIP)

**用途：** Pod 通信的稳定网络端点

**工作原理：**
1. Service 选择器匹配 Pod 标签：`app: model-api`
2. Service 创建 Endpoints 对象，列出 Pod IP
3. kube-proxy 配置 iptables 规则实现负载均衡
4. 创建 DNS 条目：`model-api-service.ml-serving.svc.cluster.local`

**负载均衡算法：**
- **默认：** 在健康端点间轮询
- **会话亲和性：** 可选的基于 ClientIP 的亲和性

**服务发现：**
```bash
# 集群内任意 Pod 均可访问：
curl http://model-api-service/health
curl http://model-api-service.ml-serving/health
curl http://model-api-service.ml-serving.svc.cluster.local/health
```

### 3. Service (LoadBalancer)

**用途：** 应用的对外访问

**云提供商集成：**
- **AWS EKS：** 预置 Classic ELB 或 Network Load Balancer
- **GCP GKE：** 预置 TCP/UDP Load Balancer
- **Azure AKS：** 预置 Azure Load Balancer

**行为：**
```yaml
spec:
  type: LoadBalancer
  ports:
  - port: 80           # 外部端口
    targetPort: 5000   # 容器端口
  selector:
    app: model-api
```

**流量流向：**
```
互联网 → 云负载均衡器 (x.x.x.x:80) → 节点 IP:NodePort → Pod IP:5000
```

### 4. Ingress (NGINX)

**用途：** HTTP/HTTPS 路由和 SSL/TLS 终止

**为何使用 Ingress：**
- **成本效率：** 多个服务共享单个负载均衡器
- **高级路由：** 基于路径、基于主机的路由
- **SSL/TLS 终止：** 集中式证书管理
- **速率限制：** 请求限流和保护

**路由规则：**
```yaml
spec:
  rules:
  - host: model-api.example.com
    http:
      paths:
      - path: /predict
        pathType: Prefix
        backend:
          service:
            name: model-api-service
            port:
              number: 80
```

**Ingress 控制器架构：**
```
┌────────────────────────────────────────┐
│   Ingress 控制器 (NGINX Pod)          │
│                                        │
│   - 监听 Ingress 资源                   │
│   - 生成 nginx.conf                    │
│   - 变更时重新加载 NGINX                │
│   - 暴露 LoadBalancer Service           │
└────────────────────────────────────────┘
```

### 5. Horizontal Pod Autoscaler (HPA)

**用途：** 根据指标自动调整副本数量

**控制循环：**
```
┌─────────────────────────────────────────────────────────────┐
│                    HPA 控制循环                              │
│                                                             │
│  1. 每 15 秒：                                              │
│     - 查询 Metrics Server 获取当前 CPU/内存                  │
│     - 计算：当前值 / 目标值 = 比率                           │
│                                                             │
│  2. 计算期望副本数：                                        │
│     desiredReplicas = ceil(currentReplicas * ratio)        │
│                                                             │
│  3. 应用伸缩策略：                                          │
│     - 检查最小/最大限制 (3-10)                               │
│     - 应用稳定窗口                                         │
│     - 应用扩容/缩容策略                                     │
│                                                             │
│  4. 必要时更新 Deployment                                   │
└─────────────────────────────────────────────────────────────┘
```

**计算示例：**
```
当前副本数: 3
当前 CPU: 85% (高于 70% 的目标)
比率: 85 / 70 = 1.21

期望副本数 = ceil(3 * 1.21) = 4

操作: 从 3 扩容至 4 个 Pod
```

**伸缩行为：**
```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0      # 立即扩容
    policies:
    - type: Percent
      value: 100                       # 可翻倍 Pod 数量
      periodSeconds: 30
    - type: Pods
      value: 2                         # 或最多增加 2 个 Pod
      periodSeconds: 30
    selectPolicy: Max                  # 使用最激进的策略

  scaleDown:
    stabilizationWindowSeconds: 300    # 缩容前等待 5 分钟
    policies:
    - type: Percent
      value: 50                        # 最大减少 50%
      periodSeconds: 60
```

### 6. ConfigMap

**用途：** 外部配置管理

**优势：**
- **关注点分离：** 配置与代码分离
- **环境特定：** 不同环境（开发/预发布/生产）的不同配置
- **无需重建镜像：** 更新配置无需新镜像
- **Kubernetes 原生：** 与 Pod 生命周期集成

**使用模式：**

**模式 1：环境变量**
```yaml
env:
- name: MODEL_NAME
  valueFrom:
    configMapKeyRef:
      name: model-config
      key: model_name
```

**模式 2：卷挂载（用于文件）**
```yaml
volumes:
- name: config-volume
  configMap:
    name: model-config

volumeMounts:
- name: config-volume
  mountPath: /etc/config
```

**配置版本控制：**
在 ConfigMap 变更时触发 Pod 更新：
1. 向 Pod 模板添加校验和注解
2. 在名称中使用 ConfigMap 哈希（ConfigMap-v2-abc123）
3. 使用 Reloader 等工具监控 ConfigMap

### 7. 健康检查

**用途：** 监控应用健康状态并控制流量路由

#### 存活探针
**使用场景：** 检测死锁或不可恢复的错误

**配置：**
```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 5000
  initialDelaySeconds: 30    # 等待启动
  periodSeconds: 10          # 每 10 秒检查一次
  timeoutSeconds: 5          # 5 秒超时
  failureThreshold: 3        # 连续 3 次失败后重启
```

**行为：**
- **成功：** Pod 继续运行
- **失败（连续 3 次）：** Kubernetes 重启容器
- **重启策略：** Always（Deployment 默认）

**实现：**
```python
@app.route('/health')
def health():
    # 检查应用是否响应
    # 不仅仅是返回 200 - 需要验证内部状态
    if not model_loaded:
        return jsonify({"status": "unhealthy"}), 500
    return jsonify({"status": "healthy"}), 200
```

#### 就绪探针
**使用场景：** 在启动/关闭期间控制流量路由

**配置：**
```yaml
readinessProbe:
  httpGet:
    path: /health
    port: 5000
  initialDelaySeconds: 10    # 比存活探针更快
  periodSeconds: 5           # 更频繁的检查
  timeoutSeconds: 3
  failureThreshold: 3
```

**行为：**
- **成功：** Pod 被添加到 Service 端点（接收流量）
- **失败：** Pod 从 Service 端点中移除（无流量）
- **不重启：** Pod 继续运行，只是不接收流量

**使用场景：**
- 模型加载（大型模型需要时间）
- 数据库连接建立
- 缓存预热
- 依赖检查

**就绪探针的流量流程：**
```
Pod 生命周期：
1. Pod 创建 → 未就绪 → 无流量
2. 容器启动 → 就绪探针开始
3. 模型加载（20 秒）
4. 就绪探针成功 → 就绪 → 接收流量
5. 关闭期间 → 就绪探针失败 → 优雅排空流量
```

  - from:

  - to:

### 自动伸缩决策树

```
┌──────────────────────────────────────────────┐
│    HPA 检查指标（每 15 秒）                    │
└──────────────┬───────────────────────────────┘
               │
               ▼
      ┌────────────────────┐
      │ 当前 CPU > 70%?    │
      └────────┬───────────┘
               │
        ┌──────┴──────┐
        │             │
       是            否
        │             │
        ▼             ▼
┌────────────────┐  ┌────────────────┐
│ 扩容           │  │ 当前           │
│ 决策           │  │ CPU < 70%?    │
└───────┬────────┘  └───────┬────────┘
        │                   │
        ▼            ┌──────┴──────┐
┌────────────────┐  │             │
│ 已达最大(10)?  │ 是            否
└───────┬────────┘  │             │
        │           ▼             ▼
   ┌────┴────┐  ┌────────────┐  ┌────────────┐
   │         │  │ 等待 5 分钟 │  │ 无操作    │
  是        否  │ 然后缩容   │  └────────────┘
   │         │  └────────────┘
   ▼         ▼
┌─────────┐  ┌────────────┐
│ 无操作   │  │ 添加 Pod   │
└─────────┘  └────────────┘
```

### 伸缩容量规划

```
每个 Pod 的资源需求：
- CPU Request：500m
- 内存 Request：1Gi

集群容量（示例 3 节点集群）：
- 节点 CPU：每节点 4 核 = 总共 12 核
- 节点内存：每节点 16Gi = 总共 48Gi
- 系统预留：约 1 核、约 4Gi = 可用 11 核、44Gi

最大 Pod 数（CPU 受限）：
11 核 / 每 Pod 0.5 核 = 最多 22 个 Pod

最大 Pod 数（内存受限）：
44Gi / 每 Pod 1Gi = 最多 44 个 Pod

实际限制：22 个 Pod（受 CPU 约束）

HPA 最大值：10 个 Pod（远在集群容量内）
```

## 高可用设计

### 故障场景与恢复

#### 场景 1：单个 Pod 故障
```
事件：Pod 因 OOM 错误崩溃
检测：存活探针失败（30 秒）
操作：Kubernetes 重启容器
恢复时间：60 秒（重启 + 就绪）
影响：无影响（其他 2 个 Pod 仍在服务）
```

#### 场景 2：节点故障
```
事件：节点无响应
检测：节点标记为 NotReady（40 秒）
操作：Pod 重新调度到健康节点
恢复时间：5 分钟（Pod 驱逐超时）
影响：恢复期间容量降低
缓解措施：超额配置副本（最少 3 个）
```

#### 场景 3：部署故障
```
事件：新版本存在 Bug，就绪探针失败
检测：就绪探针失败
操作：滚动更新暂停，不终止旧 Pod
恢复时间：立即（回滚命令）
影响：无影响（旧版本仍在运行）
```

### 可用性计算

```
假设条件：
- 最少 3 个 Pod
- 每个 Pod：99% 的单独可用性
- 独立故障

可用性 = 1 - (1 - 0.99)³ = 1 - 0.000001 = 99.9999%

考虑 Pod 恢复（60 秒）和节点故障（5 分钟）后：
有效可用性 ≈ 99.95%

远超 99.9% 的 SLA 要求
```

## 设计决策与权衡

### 1. 副本数量：最少 3 个
**理由：**
- 可容忍 1 个 Pod 故障而不影响服务
- 允许零停机滚动更新
- 平衡成本与可用性

**权衡：**
- 比 1-2 个副本成本更高
- 消耗更多资源
- 优点：更高的可用性

---

### 2. HPA 指标：CPU 70%，内存 80%
**理由：**
- 70% CPU 为突增预留余量
- 80% 内存可防止 OOM 杀死
- 不同阈值考虑了指标特性

**权衡：**
- 较低阈值 = 更多 Pod = 更高成本
- 较高阈值 = 过载风险
- 平衡：响应迅速而不过度预配

---

### 3. 滚动更新：maxSurge=1, maxUnavailable=0
**理由：**
- maxSurge=1：更新期间最少额外资源
- maxUnavailable=0：保证零停机

**权衡：**
- 更新较慢（一次一个 Pod）
- 更新期间资源使用更高
- 优点：绝对的零停机保证

---

### 4. 资源限制：2 倍 Requests
**理由：**
- 允许突发以应对高峰
- 防止资源失控消耗
- 基于观察到的使用模式

**权衡：**
- 在合理高峰时可能被限流
- 可能允许一些噪声邻居问题
- 平衡：保护而不过度限制
