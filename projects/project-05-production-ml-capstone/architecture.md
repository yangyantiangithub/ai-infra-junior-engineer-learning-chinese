## 执行摘要

本文档描述了一个生产级 ML 系统的架构，该系统将模型服务、编排、ML 流水线和可观测性集成到一个统一平台中，能够：

- 每秒提供 1000+ 次预测
- 维持 99.9% 的可用性
- 自动训练和部署模型
- 根据需求从 3 个扩展到 20 个副本
- 提供所有组件的完整可观测性

### 关键架构原则

1. **云原生**：基于 Kubernetes、容器化、水平可扩展
2. **GitOps**：基础设施和配置即代码
3. **默认安全**：认证、加密、最小权限
4. **可观测性优先**：所有组件的指标、日志和追踪
5. **自动化**：CI/CD、ML 生命周期、扩缩容、恢复
6. **韧性**：高可用性、容错、自动自愈

## 数据流

### 预测请求流

```
1. 客户端 → HTTPS 请求 → NGINX Ingress
   ├─ TLS 终止
   ├─ 限流检查
   ├─ API 密钥验证
   └─ 路由到 Service
       ▼
2. Service → 负载均衡 → API Pod
   ├─ 就绪检查
   └─ 转发请求
       ▼
3. API Pod → 处理请求
   ├─ 验证输入（文件类型、大小）
   ├─ 预处理（调整大小、归一化）
   ├─ 加载模型（从缓存或 MLflow）
   ├─ 执行推理
   ├─ 格式化响应
   └─ 记录指标
       ▼
4. 响应 → Service → Ingress → 客户端
   └─ 包含请求头：X-Model-Version、X-Request-ID
```

**延迟分解（目标）：**
- Ingress：<10ms
- 预处理：<20ms
- 模型推理：<100ms
- 后处理：<10ms
- **总计（P95）：<500ms**

### 模型训练与部署流

## 灾难恢复

### 备份策略

**需要备份的内容：**
1. **数据库（PostgreSQL）** — MLflow 元数据
2. **对象存储（S3/MinIO）** — 模型工件
3. **Kubernetes 资源** — Deployment、ConfigMap、Secret
4. **Git 仓库** — 代码和配置（已版本管理）

**备份计划：**
- 每日自动备份（UTC 时间凌晨 2 点）
- 每周完整备份（周日 UTC 时间凌晨 1 点）
- 每月快照（每月 1 日）

**备份保留期：**
- 每日备份：7 天
- 每周备份：4 周
- 每月备份：12 个月

**备份存储：**
- 主备份：同区域的 S3/GCS
- 辅助备份：不同区域的 S3/GCS（灾难恢复）

### 恢复流程

**RTO（恢复时间目标）：** <1 小时
**RPO（恢复点目标）：** <24 小时

**恢复场景：**

1. **Pod 故障**（自动，<30 秒）
   - Kubernetes 自动重启 Pod
   - 无需手动干预

2. **节点故障**（自动，<2 分钟）
   - Kubernetes 将 Pod 重新调度到健康节点
   - 无需手动干预

3. **数据库故障**（<10 分钟）
   - 将副本提升为主节点
   - 更新连接字符串
   - 重启依赖服务

4. **完整集群故障**（<1 小时）
   - 部署新集群
   - 从备份恢复（数据库、配置）
   - 部署应用
   - 验证功能

## 技术决策

### 架构决策记录（ADR）

#### ADR-001：使用 Kubernetes 进行编排

**决策：** 使用 Kubernetes 作为容器编排平台

**理由：**
- 容器编排的行业标准
- 出色的自动扩缩容和自愈能力
- 丰富的生态系统（Helm、Operator、监控工具）
- 云无关（可在 GKE、EKS、AKS 或本地运行）
- 强大的社区支持

**考量过的替代方案：**
- Docker Swarm：更简单但功能较少
- Nomad：不错但生态系统较小
- ECS/Fargate：特定云厂商，供应商锁定

---

#### ADR-002：使用 MLflow 作为模型注册表

**决策：** 使用 MLflow 进行实验跟踪和模型注册

**理由：**
- 开源，供应商中立
- 支持多种 ML 框架（PyTorch、TF、sklearn）
- 良好的实验比较 UI
- REST API 提供编程访问
- 模型版本管理和元数据跟踪

**考量过的替代方案：**
- Weights & Biases：很好但专有/昂贵
- Neptune.ai：专有
- 自建方案：维护成本过高

---

#### ADR-003：使用 Prometheus + Grafana 进行监控

**决策：** 使用 Prometheus 采集指标，Grafana 进行可视化

**理由：**
- CNCF 毕业项目（生产就绪）
- 拉取式指标（无需客户端配置）
- PromQL 查询功能强大
- Grafana 仪表盘表现优异
- 与 Kubernetes 良好集成

**考量过的替代方案：**
- Datadog：昂贵，供应商锁定
- New Relic：昂贵
- 自建方案：重复造轮子

---

#### ADR-004：使用 GitHub Actions 实现 CI/CD

**决策：** 使用 GitHub Actions 作为 CI/CD 流水线

**理由：**
- 与 GitHub 集成（代码所在之处）
- 公共仓库免费，私有仓库价格合理
- 丰富的 Action 市场
- 基于 YAML，易于版本控制
- 内置密钥管理

**考量过的替代方案：**
- GitLab CI：不错但需要 GitLab
- Jenkins：功能强大但复杂，需自托管
- CircleCI：不错但对大团队来说昂贵

---

#### ADR-005：使用 Kustomize 管理多环境配置

**决策：** 使用 Kustomize 管理环境特定配置

**理由：**
- 内置于 kubectl（无需单独工具）
- 覆盖模式保持配置 DRY
- 无模板语言（纯 YAML）
- 适合 GitOps 工作流

**考量过的替代方案：**
- Helm：更复杂，模板容易出错
- 自定义脚本：难以维护
- 环境变量：不足以满足所有配置
