## 系统概述

### 目的

监控与告警系统为 ML 基础设施提供全面的可观测性，支持：

- **实时可见性**，了解系统健康与性能
- **主动告警**，在问题影响用户之前发现
- **根因分析**，通过指标和日志关联
- **性能优化**，基于历史趋势
- **合规性**，符合 SLA 和 SLO

### 关键原则

1. **四大黄金信号**：监控延迟、流量、错误、饱和度
2. **USE 方法**：资源的利用率、饱和度、错误
3. **RED 方法**：服务的速率、错误、时长
4. **可操作的告警**：每个告警都需要人工干预
5. **基于症状的告警**：针对用户可见的症状告警，而非内部指标

### 1. 指标采集层

```
┌────────────────────────────────────────────────────────────┐
│                    指标采集架构                              │
└────────────────────────────────────────────────────────────┘

┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│    应用      │     │  基础设施    │     │   ML 模型    │
│              │     │   （节点）    │     │              │
└──────┬───────┘     └──────┬───────┘     └──────┬───────┘
       │                    │                     │
       │ /metrics           │ /metrics            │ /metrics
       │                    │                     │
       └────────────────────┼─────────────────────┘
                            │
                ┌───────────▼──────────┐
                │    Prometheus        │
                │                      │
                │  ┌────────────────┐ │
                │  │  采集目标       │ │
                │  ├────────────────┤ │
                │  │ node-exporter  │ │
                │  │ app:5000       │ │
                │  │ ml-api:8000    │ │
                │  └────────────────┘ │
                │                      │
                │  ┌────────────────┐ │
                │  │ TSDB 存储      │ │
                │  │（30天保留）    │ │
                │  └────────────────┘ │
                │                      │
                │  ┌────────────────┐ │
                │  │  告警规则       │ │
                │  └────────┬───────┘ │
                └───────────┼──────────┘
                            │
                ┌───────────▼──────────┐
                │   Alertmanager       │
                └──────────────────────┘
```

**组件**：

- **Prometheus Server**：时序数据库和采集器
  - 每 15 秒从目标拉取指标
  - 本地存储，保留 30 天
  - 每 30 秒评估告警规则

- **Exporter（导出器）**：以 Prometheus 格式暴露指标
  - `node_exporter`：系统指标（CPU、内存、磁盘）
  - `blackbox_exporter`：端点健康检查（可选）
  - 应用内置 `/metrics` 端点

- **服务发现**：自动检测目标
  - Kubernetes SD：发现 K8s 中的 Pod/服务
  - File SD：静态配置文件
  - DNS SD：通过 DNS 进行服务发现

**组件**：

- **Filebeat**：轻量级日志采集器
  - 监控日志文件变化
  - 添加元数据（主机名、标签）
  - 下游故障时本地缓冲
  - 发送到 Logstash 或 Elasticsearch

- **Logstash**：日志处理流水线
  - 解析 JSON 日志
  - 过滤敏感数据
  - 丰富附加上下文
  - 路由到 Elasticsearch

- **Elasticsearch**：分布式搜索和分析
  - 按每日索引存储日志
  - 全文搜索能力
  - 聚合分析
  - 使用 ILM 保留 90 天

- **Kibana**：可视化和探索
  - 搜索和过滤日志
  - 构建可视化
  - 创建仪表盘
  - 保存搜索

```
┌─────────────────────────────────────────────────────────────┐
│                    告警流转过程                              │
└─────────────────────────────────────────────────────────────┘

   ┌────────────────────────────────┐

   │     summary: "High errors!"    │

   ┌────────────────────────────────┐

   │ Result: 0.06 (6%)              │
   │                                │
   │ 0.06 > 0.05 → TRUE             │
   │ Duration: 5m → FIRE ALERT      │
   └────────────────────────────────┘
                │
                │ 发送到 Alertmanager
                ▼
3. Alertmanager 路由
   ┌────────────────────────────────┐
   │ Alert: HighErrorRate           │
   │ Severity: critical             │
   │                                │
   │ 路由规则:                      │
   │ - critical → PagerDuty         │
   │ - critical → Slack             │
   │                                │
   │ 分组：等待 10 秒收集相似告警   │
   │ 限流：每小时最多 1 次          │
   └────────────────────────────────┘
                │
                │ 通知接收器
                ▼
4. 发送通知
   ┌────────────────────────────────┐
   │ PagerDuty: Incident #12345     │
   │ ┌────────────────────────────┐ │
   │ │ CRITICAL: High Error Rate  │ │

   │ │ Error rate is 6% (>5%)     │ │
   │ │ Runbook: http://...        │ │
   │ │                            │ │
   │ │ [Acknowledge] [Resolve]    │ │
   │ └────────────────────────────┘ │
   │                                │
   │ Slack #alerts-critical         │
   │ ┌────────────────────────────┐ │
   │ │ 🚨 CRITICAL ALERT          │ │
   │ │ High Error Rate Detected   │ │
   │ │ Current: 6%                │ │
   │ │ Threshold: 5%              │ │
   │ └────────────────────────────┘ │
   └────────────────────────────────┘
```

## 指标架构

### 指标类型与用途

```
┌─────────────────────────────────────────────────────────────┐
│                    指标类型选择                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Counter（计数器）：单调递增                                 │
│  ┌─────────────────────────────────────────┐               │
│  │ 用途：                                   │               │
│  │ - 总请求数                               │               │
│  │ - 总错误数                               │               │
│  │ - 总预测数                               │               │
│  │                                          │               │
│  │ 查询方式：rate() 或 increase()            │               │
│  │ 示例：rate(http_requests_total[5m])      │               │
│  └─────────────────────────────────────────┘               │
│                                                             │
│  Gauge（仪表盘）：可升可降                                  │
│  ┌─────────────────────────────────────────┐               │
│  │ 用途：                                   │               │
│  │ - CPU 使用率                             │               │
│  │ - 内存使用率                             │               │
│  │ - 活跃连接数                             │               │
│  │ - 模型准确率                             │               │
│  │                                          │               │
│  │ 查询方式：直接查询或 avg()                │               │
│  │ 示例：node_memory_usage_bytes            │               │
│  └─────────────────────────────────────────┘               │
│                                                             │
│  Histogram（直方图）：值的分布                              │
│  ┌─────────────────────────────────────────┐               │
│  │ 用途：                                   │               │
│  │ - 请求时长                               │               │
│  │ - 响应大小                               │               │

│  │                                          │               │

│  └─────────────────────────────────────────┘               │
│                                                             │

```

### 指标命名规范

```
<metric_name>{label1="value1", label2="value2"}

最佳实践：
- 指标名称使用蛇形命名法（snake_case）
- 在名称中包含单位（bytes、seconds、total）
- 使用标签表示维度，而非指标名称
- 保持基数较低（< 10k 唯一标签组合）

好的示例：
✓ http_request_duration_seconds{method="GET", endpoint="/predict"}
✓ model_predictions_total{model="resnet50", class="cat"}
✓ node_memory_usage_bytes{instance="server01"}

不好的示例：
✗ httpRequestDurationSeconds（驼峰命名）
✗ requests（没有单位，没有上下文）
✗ http_get_predict_latency（维度在名称中而非标签中）
✗ user_123_requests（高基数标签）
```

## 可扩展性考虑

### Prometheus 扩展

1. **垂直扩展**：增加内存和 CPU
2. **联邦**：分层 Prometheus 实例
3. **远程写入**：长期存储到 Thanos/Cortex
4. **分片**：将采集目标分散到多个实例

### Elasticsearch 扩展

1. **添加节点**：水平扩展到 3、5、7 个节点
2. **热-温-冷架构**：按年龄分层存储
3. **索引生命周期管理（ILM）**：自动管理索引
4. **分片调优**：优化分片大小（每分片 20-50GB）

### Grafana 扩展

1. **数据库后端**：使用 PostgreSQL 替代 SQLite
2. **缓存**：启用查询缓存
3. **负载均衡**：多个 Grafana 实例
4. **CDN**：从 CDN 提供静态资源
